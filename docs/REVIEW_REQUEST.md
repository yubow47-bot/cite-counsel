## Problem

Two issues found in the expand_concept() Gemini call:

### 1. Hash-comment leak inside prompt f-string
Lines ~245-253 of `citation_search.py` contained 9 lines of `# ...` hash-prefixed text that was intended as a Python code comment (documenting the limits of the citation-number proximity prompt rule) but was accidentally placed INSIDE the f-string. This meant ~150 tokens of meta-commentary were being sent to Gemini on every concept query as literal prompt content, adding confusing text and consuming thinking time.

### 2. read_timeout=12s too tight for broad concepts
Diagnostic testing confirmed:
- Narrow concepts (oakes test 6.96s, gladue principle 8.60s) are safe at 12s
- Broad doctrinal concepts (mens rea 10.34s, negligence 12.40s) fall at or over the boundary
- Result: 4/4 mens rea runs hit timeout, triggering slow DeepSeek fallback (17-26s) → 32-40s end-to-end, WORSE than pre-Gemini baseline (21.9s)

## Fix

### 1. Hash lines moved to real Python comment
The 9 lines were removed from inside the f-string and placed as a proper Python comment (using `#` outside any string literal) before the `prompt = f"""` definition. The prompt sent to Gemini shrank from 3680 → 2972 chars (~700 chars / ~100 tokens saved).

### 2. read_timeout raised to 20s
Changed from 12s to 20s based on measured broad-concept response times (13-18s). connect_timeout (5s) and thinking_budget (4096) unchanged.
