## Round 3: concept-route legislation shows pinpoint twice

### Bug

Query "gladue principle" → the Criminal Code candidate is formatted as
"Criminal Code, RSC 1985, c C-46, s 718.2(e) s 718.2(e)." — the pinpoint
appears twice.

### Root cause

In `_verify_legislation()` (inside `expand_concept()`), `extract_pinpoint()`
extracts the pinpoint suffix into `entry["pinpoint"]`, but the LLM-provided
`name` still carries the full string (e.g. `"Criminal Code, RSC 1985,
c C-46, s 718.2(e)"`). Both fields flow into `format_citation()`, which
includes the pinpoint once from the embedded text and once from the
separate `pinpoint` field → duplicate.

### Fix

After extracting `_pin` and setting `entry["pinpoint"]`, if both `_pin`
and `cit_match` are truthy, overwrite `entry["name"]` with the clean base
citation text:

```python
if _pin and cit_match:
    entry["name"] = normalized[:cit_match.end()].strip().rstrip(',').strip()
```

This strips the pinpoint suffix from `name` while keeping it available as
a separate `pinpoint` field. No other code paths are modified.

## Frontend Pinpoint UI Finding

**`frontend/components/citation-card.tsx` does NOT distinguish by
`source_type` when showing the editable pinpoint box.** The `useEffect` at
lines 122–127 unconditionally prefills `pinpointText` from `item.pinpoint`
and opens the input whenever `item.pinpoint` is truthy, regardless of
whether the citation text already embeds the pinpoint (legislation/concept
routes) or not (case route).

For legislation/concept routes, the API intentionally passes pinpoint
through to `format_citation` so the LLM includes it in the citation text
(see the comment in `api/main.py` line 411). But the API also returns
`pinpoint` as a separate response field, causing the frontend to display
an editable pinpoint box that, when the user clicks Copy, concatenates the
pinpoint a second time.

**Recommendation (not yet implemented — needs product decision):**

The cleanest fix is in the backend, not the frontend: for legislation and
concept routes where the pinpoint has already been consumed by
`format_citation`, the API should omit `pinpoint` from the response data.
This avoids the concatenation entirely without needing to add frontend
route-awareness. The pinpoint is still available for internal use (it's
already part of the formatted `citation` string sent to the client).

If a frontend-only fix is preferred instead, two options:

1. **Suppress the editable pinpoint box for legislation/concept routes**
   by checking `item.source_type` before showing the "Add pinpoint" UI.
2. **Add a `pinpointEmbedded` boolean to the API response** so the
   frontend can distinguish "pinpoint is a separate add-on" (case route)
   from "pinpoint is already part of the citation text" (legislation/
   concept route), and suppress the UI accordingly.

Both frontend options are straightforward but change user-facing behavior
and should be confirmed before implementation.
