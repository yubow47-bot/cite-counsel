## Goal

Fix `_handle_concept` to return `needs_selection` when multiple concept-expansion candidates are returned, matching the behaviour of the `case_name` route. Previously concept results were formatted immediately and returned as `done`, skipping the user's ability to choose between candidates.

* `api/main.py` — `_handle_concept()`: empty → needs_input (unchanged), single → done (simplified), multiple → needs_selection (new, mirrors case_name)
* `tests/test_concept_selection.py` — new; 3 FastAPI TestClient tests (multi→needs_selection, single→done, zero→needs_input)

## Architecture Impact

Yes — this fix aligns the concept route's multi-result handling with `case_name`, changing the timing of `format_citation` from immediate (inside `_handle_concept`) to deferred (on user selection via `/api/citation/select`). Impact is limited to `api/main.py::_handle_concept()`; the `classify → route → search → format` pipeline stages are unchanged.

## Risk Declaration

* The removed `source_case` field in the response (previously `{"citation": ..., "source_case": source}` per item) is no longer returned in the multi-result path — the `display` field now serves the same purpose. Any frontend code relying on `source_case` in the concept response would need updating, but the existing frontend does not consume it (it uses `candidates[].display` for `case_name`).
